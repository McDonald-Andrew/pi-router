# Raspberry Pi Image User Guide

Do not use an image whose checksum does not match or whose provenance and
Imager manifests do not identify the expected router version.

Current engineering builds use the `development` profile, whose filename ends in `-development.img.xz`, or the `release` profile, which uses the intended final filename but remains explicitly uncertified in its manifest. When testing one, use its exact builder-produced name in the commands below; never rename a development artifact to look certified.

## Build the image yourself

You can build the same four-file image set from a committed, clean checkout instead of downloading a published release. The builder requires Debian or Ubuntu Linux. On Windows, run it through Ubuntu under WSL.

From PowerShell, enter Ubuntu:

```powershell
wsl -d Ubuntu
```

Then run the following inside Ubuntu. Replace the repository path and `X.Y.Z` with your checkout and intended version:

```bash
cd /mnt/c/path/to/pi-router

sudo apt-get update
sudo apt-get install --no-install-recommends \
    curl fdisk git kmod mount python3 python3-jsonschema \
    systemd udev util-linux xz-utils

mkdir -p image-output "$HOME/pi-router-image-work"

df -h "$HOME"
sudo modprobe loop 2>/dev/null || true
sudo losetup --find

bash image/build-local \
    X.Y.Z \
    "$PWD/image-output" \
    "$HOME/pi-router-image-work" \
    release
```

The checkout must have no uncommitted changes under `src/` or `image/`. Keep `pi-router-image-work` on WSL's native Linux filesystem with about 16 GiB free; do not place it under `/mnt/c`. The output directory may remain inside the Windows checkout so Raspberry Pi Imager can access the completed files.

The first build downloads and verifies the pinned Raspberry Pi OS image. Later builds reuse that download from `pi-router-image-work`. A complete build customizes the image, compresses it, and performs the final read-only audit. Successful completion produces:

```text
image-output/pi-router-vX.Y.Z-pi5-arm64.img.xz
image-output/pi-router-vX.Y.Z-pi5-arm64.img.xz.sha256
image-output/pi-router-vX.Y.Z-pi5-arm64.manifest.txt
image-output/pi-router-vX.Y.Z-pi5-arm64.rpi-imager-manifest
```

## Verify the download

On Windows PowerShell:

```powershell
$image = "pi-router-vX.Y.Z-pi5-arm64.img.xz"
$sidecar = "$image.sha256"
$expected = ((Get-Content -LiteralPath $sidecar -Raw).Trim() -split '\s+')[0]
$actual = (Get-FileHash -LiteralPath $image -Algorithm SHA256).Hash

if ($actual -ine $expected) {
    throw "Pi Router image checksum mismatch"
}
```

On Linux, keep the image and checksum sidecar in the same directory:

```bash
sha256sum --check pi-router-vX.Y.Z-pi5-arm64.img.xz.sha256
```

The release manifest records both compressed and extracted hashes and sizes. Published values must come from the release; do not substitute placeholder values from this guide.

## Write the microSD card

This flow requires Raspberry Pi Imager 2.x. Do not select the raw `.img.xz`
through **Use Custom**: Imager treats an un-described local image as not supporting OS customization.

1. Download and open the `.rpi-imager-manifest` with Raspberry Pi Imager. On Windows, you can double-click the manifest after installing Imager. Alternatively, open Imager's **App Options**, choose **Content Repository**, and select the custom manifest file.
   - The image will ship with a `.rpi-imager-manifest` that mirrors the matching official Raspberry Pi OS Desktop entry's customization behavior.
2. Confirm that you intend to use the trusted repository, then select the Raspberry Pi 5 and the Pi Router OS entry supplied by that manifest.
3. In OS customization, set the username to exactly `admin`, choose a unique password, and choose whether SSH is disabled, password-based, or key-based.
4. Select the intended microSD card under **Choose Storage**.
5. Start the write and allow Imager to verify it.
6. Eject the card safely and insert it into the powered-off Pi.

The OS password is handled by Raspberry Pi Imager and the official first-boot customization mechanism. The later Pi Router browser page asks only for Proton credentials.

## Connect the final topology

Make all connections before applying power:

```text
Internet modem or upstream router
              |
              | WAN
              v
Waveshare PCIe Ethernet port
        Raspberry Pi 5
built-in Ethernet port
              |
              | LAN
              v
downstream access point or switch
              |
              v
       onboarding browser
```

The downstream access point must operate strictly be in Access-Point (AP) mode. A competing DHCP server can prevent the browser from joining the Pi Router provisioning LAN.

Keep the downstream network physically controlled during onboarding. The temporary site uses a unique self-signed certificate generated by the Pi. It encrypts the credentials, but the first connection cannot authenticate the Pi against any attacker already present on the LAN.

## First boot and Proton onboarding

1. Power the upstream modem/router and allow it to finish starting.
2. Power the downstream access point or switch.
3. Power the Pi Router.
4. Allow the Pi to complete its pre-reboot work and automatic first reboot.
5. Connect a browser device only to the downstream LAN. Renew its DHCP lease or briefly reconnect it after the reboot if it does not receive a provisioning address.
6. Visit `https://192.168.50.1:8443`. The site becomes available only after that first reboot and the local desktop/onboarding services are ready.
7. Continue past the one-time self-signed-certificate warning only when the browser is attached to the physically trusted downstream LAN.
8. Wait until the page reports **Ready for Proton sign-in**.
9. Enter the Proton username and password. Do not let the browser save the password for the router address.
10. Leave both Ethernet cables connected and do not remove power while the Pi verifies Proton and performs its final reboot.

The page reports hardware, cable, WAN, setup, and sanitized error status. A failed Proton authentication attempt remains in provisioning mode and permits another attempt. It does not promote normal LAN gateway or DNS service.

After successful sign-in the Pi reboots, waits for its production services and Proton tunnel, and runs the canonical final verification. Normal operation is authorized only after `FINAL VERIFICATION PASSED` and the image-owned ready receipt are present.

The temporary onboarding site intentionally stops before the final reboot, so its disappearance after successful Proton verification is expected. It will not display the final `ready` state. Confirm final readiness through the production interface once that interface is certified, or through the local state receipt during development certification.

## Waiting and retry behavior

- **Missing LAN cable:** setup remains fail-closed and waits for LAN carrier.
- **Missing WAN cable or route:** setup remains fail-closed and waits for WAN.
- **No repository connectivity:** setup retries after connectivity returns.
- **Invalid Proton credentials:** the same browser session may try again.
- **Reboot in progress:** the temporary page can disappear while the Pi restarts. After successful Proton verification it remains unavailable; do not submit credentials again unless it explicitly returns to the sign-in state.
- **Terminal setup error:** normal routing remains disabled. Record the sanitized error code before recovering or reimaging.

Cable and upstream-network waits intentionally resume when connectivity is restored. A malformed or contradictory setup checkpoint is not repaired by the image controller; reimage the card in that case.

## Local diagnostics

SSH is disabled and the exported image deliberately locks `admin`. The local
commands below are available only if the certified graphical autologin/session
provides a usable terminal, or when using a controlled development/debug image:

```bash
sudo systemctl status pi-router-firstboot.service
sudo systemctl status pi-router-firstboot.timer
sudo systemctl status pi-router-onboarding-backend.service
sudo systemctl status pi-router-onboarding.service
sudo journalctl -u pi-router-firstboot.service -b --no-pager
sudo journalctl -u pi-router-onboarding-backend.service -b --no-pager
sudo cat /var/lib/pi-router-image/state
sudo cat /var/lib/pi-router-image/status
sudo cat /var/lib/pi-router-image/error
```

Some state files are absent until their corresponding transition occurs. The image-owned records contain bounded status and error enums, not Proton credentials. Still review diagnostic output before sharing it publicly.

If the `admin` account or selected SSH mode is not usable, reimage the card and re-enter the OS customization settings. Do not add a shared password to the image or move Linux password handling into the Proton onboarding page.

If the image is corrupt, identity generation fails, or checkpoint integrity is lost, write a freshly verified image to the card rather than editing setup-owned state by hand.
